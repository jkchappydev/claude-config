# 일일 업무 보고

## 저장

`docs/report/YYYY-MM-DD-{사용자ID}.md`

- 사용자ID는 `git config user.email`의 `@` 앞부분을 쓴다.
- 오늘 내 파일이 없으면 만들고, 있으면 기존 내용을 유지하면서 갱신한다.
- 지난 날짜 파일은 수정하지 않는다.

## 작성자

작성자명은 `git config --get report.name`을 그대로 쓴다. `git config user.name`과는 별개다.

`report.name`이 없으면 `user.name`으로 대신하거나 이름을 추측하지 말고 작성을 중단한다.

```text
업무 보고 표시 이름이 설정되어 있지 않습니다.
최초 1회 아래 명령어로 표시 이름을 설정해 주세요.

git config --global report.name "홍길동"
```

## 확인 순서

1. 오늘 기존 보고 내용
2. 해당 날짜의 내 Git commit
3. 필요한 경우 Git diff

뒤의 자료를 보고 앞의 기록을 지우지 않는다.

Git에 남지 않는 운영 DB 작업, 서버 설정, 장애 대응, 테스트, 분석도 기존 보고에 적혀 있으면 유지한다. Git은 빠진 내용을 확인하는 보조 자료로만 쓴다.

## 정리 기준

- 커밋 수대로 적지 않는다. 목적이 같으면 하나의 업무로 묶는다.
- merge commit, 포맷팅, 오타, 자동 생성 파일 변경처럼 따로 보고할 필요가 없는 내용은 관련 업무에 포함하거나 생략한다.
- 한 업무는 기본 한 줄로 쓴다.
- 무엇을 했는지와 달라진 결과가 보이면 충분하다.
- 구현 위치나 클래스·메서드·파일명은 꼭 필요할 때만 적는다.
- API, 화면, DB를 같이 수정했더라도 같은 목적이면 하나로 묶는다.
- 원인과 해결 과정을 둘 다 길게 쓰지 않는다.
- 사소한 수정은 관련 업무에 포함한다.
- 너무 줄여서 무슨 작업인지 알 수 없게 만들지는 않는다.
- 작업이 많은 날도 완료된 작업 3~5개 정도로 핵심이 보이게 정리하되, 개수를 맞추려고 다른 업무를 억지로 합치지 않는다.

예:

```text
로그인 성공 후 도서목록으로 이동하지 않던 문제 수정,
게이트웨이·로그인 핸들러·클라이언트의 리다이렉트 경로 보정
→ 로그인 성공 후 도서목록으로 이동하지 않던 리다이렉트 오류 수정

도서 목록 조회 성능 개선
→ 도서 목록 조회 성능 개선, 전체 조회 구조를 2단계로 변경
```

## 문체

사내에서 개발자가 직접 적은 업무보고처럼 쓴다.

- 쉬운 표현을 쓴다.
- 문장을 필요 이상으로 매끈하게 만들지 않는다.
- 모든 항목을 같은 틀로 맞추지 않는다.
- 원인 → 조치 → 결과를 매번 갖춰 쓰지 않는다.
- `—`, `:`, `→` 같은 기호를 문장마다 반복하지 않는다.
- `반영`, `해소`, `고도화`, `정비`처럼 딱딱한 표현은 평소 쓰는 말로 바꿔도 뜻이 같으면 쉬운 쪽을 쓴다.
- 기술 용어는 실제 업무에서 쓰는 표현 그대로 둔다.
- `~했음`, `이거 수정` 같은 개인 메모체는 쓰지 않는다.

예:

```text
운영 DB에서 구 테이블을 참조하던 잔존 FK 6개 정리 — 모두의서평 등록 실패 해소
→ 운영 DB에 남아있던 구 테이블 FK 6개 정리, 모두의서평 등록 오류 수정
```

## 시행착오와 결정

최종 결과에 영향이 없는 시행착오는 적지 않는다.

- 잘못 짚은 원인이나 실패한 구현
- 수정했다가 되돌린 과정
- 단순 병합 과정
- 임시 우회 방법

대신 이후 작업에 영향을 주는 내용은 남긴다.

- 이번 범위에서 의도적으로 제외한 기능
- 추가 작업이 필요한 범위
- 정책 결정이 필요한 사항
- 기술적 제약으로 적용하지 않은 방법
- 다음 작업자가 알아야 할 결정

예: `도서 목록 조회 성능 개선, 기본 조회 구조를 2단계로 변경. 리뷰수·평균별점 정렬은 이번 범위에서 제외`

## 형식

```markdown
# YYYY-MM-DD 일일 업무 보고

작성자: {이름}

## 완료된 작업
- ...

## 진행 중 / 이슈
- [이슈명]: 현재 상황 → 다음 액션
```
