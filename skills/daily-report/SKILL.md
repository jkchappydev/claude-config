# 일일 업무 보고

## 저장

`~/.claude/daily-report/YYYY-MM-DD-{사용자ID}.md`

예: `~/.claude/daily-report/2026-08-24-honggildong.md`

업무 보고는 프로젝트 Git 저장소 안에 두지 않는다. 프로젝트에는 `docs/report/` 같은 폴더를 만들지 않는다.

- 사용자ID는 `git config user.email`의 `@` 앞부분을 쓴다.
- 하루에 여러 프로젝트를 작업해도 사용자별 일일 업무 보고 파일은 날짜당 하나만 사용한다.
- 오늘 내 파일이 없으면 만들고, 있으면 기존 내용을 유지하면서 현재 프로젝트 섹션만 갱신한다.
- 다른 프로젝트 섹션은 절대 지우거나 다시 작성하지 않는다.
- 지난 날짜 파일은 원칙적으로 수정하지 않는다.

## 프로젝트명 결정

- 현재 작업 중인 Git 저장소의 **루트 디렉터리명**을 프로젝트명으로 쓴다 (`git rev-parse --show-toplevel`로 루트를 찾고, 그 경로의 마지막 디렉터리명을 사용).
- 하위 디렉터리에서 실행하고 있어도 반드시 루트 기준으로 판단해서 같은 프로젝트명으로 기록되게 한다.
- 현재 위치가 Git 저장소가 아니어서 루트를 찾을 수 없으면, 프로젝트명을 임의로 만들지 말고 사용자에게 알린다.

```text
현재 위치가 Git 저장소가 아니라 프로젝트를 식별할 수 없습니다.
Git 저장소 안에서 다시 요청해 주세요.
```

## 프로젝트별 갱신

일일 업무 보고 파일 안에서 프로젝트를 `## {프로젝트명}` 섹션으로 구분한다.

현재 프로젝트에서 `daily-report`를 실행하면:

1. 오늘 날짜의 `~/.claude/daily-report/YYYY-MM-DD-{사용자ID}.md`를 찾는다.
2. 파일이 없으면 새로 만든다.
3. 현재 프로젝트의 `## {프로젝트명}` 섹션을 찾는다.
4. 섹션이 없으면 파일 끝에 새로 추가한다.
5. 섹션이 있으면 해당 프로젝트 내용만 갱신한다.
6. 다른 프로젝트 섹션과 그 내용을 그대로 보존한다.

예:

```markdown
# 2026-08-20 일일 업무 보고

작성자: 홍길동

## project-a

### 완료된 작업
- ...

### 진행 중 / 이슈
- ...

## project-b

### 완료된 작업
- ...

### 진행 중 / 이슈
- ...
```

## 작성자

작성자명은 `git config --get report.name`을 그대로 쓴다. `git config user.name`과는 별개다.

`report.name`이 없으면 `user.name`으로 대신하거나 이름을 추측하지 말고 작성을 중단한다.

```text
업무 보고 표시 이름이 설정되어 있지 않습니다.
최초 1회 아래 명령어로 표시 이름을 설정해 주세요.

git config --global report.name "홍길동"
```

## 확인 순서

현재 프로젝트 섹션을 기준으로 다음 순서로 확인한다.

1. 오늘 기존 업무 보고의 현재 프로젝트 섹션
2. 해당 날짜의 현재 사용자 Git commit
3. staged / unstaged 변경

뒤의 자료를 보고 앞의 기록을 지우지 않는다.

Git에 남지 않는 운영 DB 작업, 서버 설정, 장애 대응, 테스트, 분석도 기존 프로젝트 섹션에 적혀 있으면 유지한다. Git은 빠진 내용을 확인하는 보조 자료로만 쓴다.

### staged / unstaged 판단 규칙

staged / unstaged 변경은 업무 내용을 파악하기 위한 보조 자료로 사용한다.

- staged / unstaged 상태라는 이유만으로 `완료된 작업`으로 판단하지 않는다.
- 오늘 Git commit으로 완료가 확인되는 작업은 완료된 작업으로 정리할 수 있다.
- staged / unstaged만 존재하는 작업은 실제 변경 내용을 확인한다.
- 완료 여부가 명확하지 않으면 임의로 완료 처리하지 않고, 필요한 경우 `진행 중 / 이슈`로 정리한다.
- 기존 업무 보고에 완료/진행 상태가 명시되어 있으면 그 기록을 우선한다.

즉 staged / unstaged는 **무슨 작업을 했는지**를 보완하는 자료이지, **완료 여부**를 자동으로 결정하는 근거가 아니다.

## 지난 날짜 업무 보고

지난 날짜 파일은 원칙적으로 수정하지 않는다.

다만 사용자가 특정 지난 날짜의 업무 보고 작성을 명시적으로 요청한 경우에는 해당 날짜 보고의 현재 프로젝트 섹션을 새로 작성하거나 보완할 수 있다.

예: `2026-08-20 일일 업무 보고 작성해줘`

- 해당 날짜 파일의 현재 프로젝트 섹션이 있으면 그 내용을 보존한다.
- 같은 파일에 다른 프로젝트 섹션이 있으면 절대 수정하거나 삭제하지 않는다.
- 해당 날짜의 현재 사용자 Git commit을 기준으로 현재 프로젝트 작업만 복원한다.
- 당시 커밋되지 않았고 기존 보고에도 없는 작업은 추측하지 않는다.
- 필요한 경우 Git에 남지 않은 작업은 복원할 수 없다고 사용자에게 알린다.
- 사용자의 명시적 요청 없이 과거 날짜 보고를 임의로 수정하지 않는다.
- 과거 날짜를 복원할 때 현재 staged / unstaged 변경을 과거 작업으로 포함하지 않는다.

## 정리 기준

- 커밋 수대로 적지 않는다. 목적이 같으면 하나의 업무로 묶는다.
- 반대로 하나의 커밋에 목적이 다른 작업이 섞여 있으면 여러 업무로 나눌 수 있다.
- 커밋 메시지를 그대로 업무 내용으로 복사하지 않는다. 필요한 경우 diff를 확인해 실제 작업 목적을 판단한다.
- 업무를 나누는 기준은 **코드 변경이 다른가**가 아니라 **업무 목적이 독립적으로 다른가**이다.
- 각 변경이 업무 보고에서 독립적으로 보고할 만한 목적을 가진 경우에만 분리한다.
- 상위 업무를 수행하면서 같이 발생한 구현 세부사항은 별도 업무로 분리하지 않는다.
- 단순 컬럼 정리, 주석처리, 의존성 정리, 내부 코드 정리 등은 관련 업무에 포함하거나 생략한다.
- 버그 수정과 기능 제거처럼 업무 목적 자체가 다른 경우에는 분리할 수 있다.
- merge commit, 포맷팅, 오타, 자동 생성 파일 변경처럼 따로 보고할 필요가 없는 내용은 관련 업무에 포함하거나 생략한다.
- 한 업무는 기본 한 줄로 쓴다.
- 무엇을 했는지와 달라진 결과가 보이면 충분하다.
- 구현 위치나 클래스·메서드·파일명은 꼭 필요할 때만 적는다.
- API, 화면, DB를 같이 수정했더라도 같은 목적이면 하나로 묶는다.
- 원인과 해결 과정을 둘 다 길게 쓰지 않는다.
- 사소한 수정은 관련 업무에 포함한다.
- 너무 줄여서 무슨 작업인지 알 수 없게 만들지는 않는다.
- 작업이 많은 날도 완료된 작업 3~5개 정도로 핵심이 보이게 정리하되, 개수를 맞추려고 다른 업무를 억지로 합치지 않는다.

예:

```text
로그인 성공 후 도서목록으로 이동하지 않던 문제 수정,
게이트웨이·로그인 핸들러·클라이언트의 리다이렉트 경로 보정
→ 로그인 성공 후 도서목록으로 이동하지 않던 리다이렉트 오류 수정

도서 목록 조회 성능 개선
→ 도서 목록 조회 성능 개선, 전체 조회 구조를 2단계로 변경
```

업무 분리 예:

```text
분리 O
- 도서 목록 조회 500 에러 수정
- 사용하지 않는 도서 카테고리 기능 제거

분리 X
- 추천도서 등록 API 500 에러 수정
- 500 에러 수정 과정에서 같이 처리한 사용하지 않는 컬럼 주석처리
```

## 문체

사내에서 개발자가 직접 적은 업무보고처럼 쓴다.

- 쉬운 표현을 쓴다.
- 문장을 필요 이상으로 매끈하게 만들지 않는다.
- 모든 항목을 같은 틀로 맞추지 않는다.
- 원인 → 조치 → 결과를 매번 갖춰 쓰지 않는다.
- `—`, `:`, `→` 같은 기호를 문장마다 반복하지 않는다.
- `반영`, `해소`, `고도화`, `정비`처럼 딱딱한 표현은 평소 쓰는 말로 바꿔도 뜻이 같으면 쉬운 쪽을 쓴다.
- 기술 용어는 실제 업무에서 쓰는 표현 그대로 둔다.
- `~했음`, `이거 수정` 같은 개인 메모체는 쓰지 않는다.

예:

```text
운영 DB에서 구 테이블을 참조하던 잔존 FK 6개 정리 — 모두의서평 등록 실패 해소
→ 운영 DB에 남아있던 구 테이블 FK 6개 정리, 모두의서평 등록 오류 수정
```

## 시행착오와 결정

최종 결과에 영향이 없는 시행착오는 적지 않는다.

- 잘못 짚은 원인이나 실패한 구현
- 수정했다가 되돌린 과정
- 단순 병합 과정
- 임시 우회 방법

대신 이후 작업에 영향을 주는 내용은 남긴다.

- 이번 범위에서 의도적으로 제외한 기능
- 추가 작업이 필요한 범위
- 정책 결정이 필요한 사항
- 기술적 제약으로 적용하지 않은 방법
- 다음 작업자가 알아야 할 결정

예: `도서 목록 조회 성능 개선, 기본 조회 구조를 2단계로 변경. 리뷰수·평균별점 정렬은 이번 범위에서 제외`

## 형식

```markdown
# YYYY-MM-DD 일일 업무 보고

작성자: {이름}

## {프로젝트명}

### 완료된 작업
- ...

### 진행 중 / 이슈
- [이슈명]: 현재 상황 → 다음 액션

## {다른 프로젝트명}

### 완료된 작업
- ...

### 진행 중 / 이슈
- ...
```
