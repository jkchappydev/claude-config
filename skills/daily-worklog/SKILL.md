# 일일 업무 보고 작성

## 파일 경로

`docs/worklog/YYYY-MM-DD-{사용자ID}.md` — 날짜와 작업자로 나눈다. 같은 프로젝트에 여러 사람이 워크로그를 써도 파일이 충돌하지 않게 하기 위함.

## 1. 작성자 판별 (파일 생성 시 1회)

중앙 매핑 파일을 두지 않고 각 사용자의 Git 설정을 기준으로 삼는다.

1. **사용자ID**(파일명용): `git config user.email`의 `@` 앞부분을 쓴다. (`jkchappy@eco.co.kr` → `jkchappy`)
2. **표시 이름**(작성자): `git config --get worklog.name` 값을 쓴다. 이 값이 있으면 반드시 그대로 사용한다.

`worklog.name`은 워크로그 표시 전용 설정이라 `user.name`(커밋 author)과 별개다. 예: `user.name`이 `jkchappy`여도 `worklog.name`이 `정근찬`이면 작성자는 `정근찬`.

### worklog.name이 없으면 — 워크로그를 만들지 말고 안내부터

`user.name`을 조용히 대신 쓰지 않는다. `user.name`은 `jkchappy`, `devhong` 같은 계정명일 수 있어 그대로 보고서에 들어가면 안 된다. 이름을 임의로 추측하지도 않는다.

워크로그 작성을 멈추고 아래를 안내한다:

```
워크로그 표시 이름이 설정되어 있지 않습니다.
최초 1회 아래 명령어로 표시 이름을 설정해 주세요.

git config --global worklog.name "홍길동"
```

한 번 등록하면 그 PC의 모든 프로젝트에 적용된다. 사용자가 추가되거나 빠져도 중앙 목록을 고치거나 커밋할 일은 없다.

## 2. 정보 출처 우선순위

작업 내용을 정리할 때 아래 순서로 참고하고, 우선순위가 낮은 자료로 높은 자료의 내용을 지우지 않는다.

1. **기존 워크로그** — 오늘 이 파일에 이미 적힌 내용(대화 중 논의·결정 등)
2. **해당 날짜의 Git commit** — 해당 작성자 이메일 기준
3. **Git 변경 내역(diff)** — 커밋 메시지만으로 뭘 했는지 불충분할 때 실제 변경 내용을 참고

Git commit이 없다고 해서 워크로그에 이미 적힌 업무(운영 DB 작업, 서버 설정 변경, 장애 대응, 테스트, 분석 등)를 빼지 않는다. Git은 워크로그를 보완하고 작업자·실제 변경사항을 확인하는 보조 자료로만 쓴다.

## 3. 커밋을 작업 단위로 묶기

- 여러 커밋이라도 목적이 같으면 하나의 작업 항목으로 합친다. 커밋 메시지, 변경 파일, 기존 워크로그 내용을 함께 보고 같은 작업인지 판단한다.
  - 예: `fix: 도서 삭제 오류 수정` / `fix: FK 처리 추가` / `fix: 댓글 cascade 추가` / `test: 삭제 테스트 수정` → "도서 삭제 기능 및 연관 데이터 삭제 처리 보완" 한 줄로 통합
- merge commit, 포맷팅, 오타 수정, 빌드 산출물 자동 변경 등 보고 가치가 낮은 커밋은 독립 항목으로 만들지 않는다 — 관련 작업에 흡수하거나 생략한다.

## 4. 작성 원칙 (간결화)

이 보고는 개발 기록이 아니라 **"오늘 무엇을 했는지 빠르게 파악"**하는 용도다. 세부 구현 과정을 재현할 수 있을 정도의 기록은 목적이 아니다.

- 한 작업은 기본적으로 한 줄. **무엇을 했는지 + 결과** 중심으로 쓴다.
- **한 줄을 유지하려고 구현 내용을 길게 나열하지 않는다.** 세부 변경이 여러 개면 전부 열거하지 말고 대표적인 조치와 결과만 남긴다.
- Controller·Service·Repository 같은 변경 위치나 클래스명·메서드명·파일명은 결과를 이해하는 데 꼭 필요할 때만 쓴다.
- API·화면·DB 등 여러 영역을 고쳤어도 하나의 목적을 위한 변경이면 영역별로 나열하지 않고 핵심 결과로 통합한다.
- 원인과 해결 방법을 둘 다 길게 쓰지 않는다. 업무 이해에 더 중요한 한쪽만으로 충분하면 하나만 남긴다.
- 사소한 수정은 독립 항목으로 만들지 않고 관련 작업 항목에 포함한다.
- 항목마다 작성자 이름을 반복해서 붙이지 않는다 — 파일 자체가 사용자별로 분리되어 있기 때문.

| 과도한 나열 | 적정 |
|---|---|
| 로그인 성공 후 도서목록으로 이동하지 않던 문제 수정 — 죽은 경로(`/main`)로 빠지던 리다이렉트를 게이트웨이·로그인 핸들러·클라이언트 3곳에서 일관되게 보정 | 로그인 성공 후 도서목록으로 이동하지 않던 리다이렉트 오류 수정 |
| 도서 삭제 기능 구현 및 release 병합 — 삭제 API와 서비스 로직, 사서베스트·추천도서·모두의서평·이달의선택투표 등록 여부에 따른 삭제 차단 검증, 댓글 cascade 삭제, 상세 페이지 삭제 버튼 연동까지 완료 | 도서 삭제 기능 구현 및 release 병합, 연관 콘텐츠가 있는 경우 삭제되지 않도록 처리 |

### 축약 하한선

압축하다가 작업의 핵심 결과나 의미까지 지우지 않는다.

- 구현 과정은 생략하되, **무엇이 달라졌는지 판단할 수 있는 정보**는 남긴다.
- "무엇을 했다"만 적고 끝내지 말고, 비중 있는 작업은 **핵심 조치나 결과 중 하나**를 함께 남긴다.

| 과도한 축약 | 적정 |
|---|---|
| 도서 목록 조회 성능 개선 | 도서 목록 조회 성능 개선, 전체 조회 구조를 2단계로 변경 |
| 도서 삭제 수정 | 도서 삭제 시 연관 콘텐츠가 있으면 삭제되지 않도록 처리 |

### 문체

잘 쓴 보고서 문장처럼 다듬지 않는다. 실제 개발자가 업무보고에 적는 정도면 충분하다.

- 격식 있거나 추상적인 표현은 피하고, 같은 뜻이면 쉬운 쪽을 쓴다. 명사형을 길게 늘어놓지 않는다.
- 모든 항목을 같은 문장 패턴으로 반복하지 않는다. 원인 → 조치 → 결과를 매번 갖춰 쓰지 않아도 된다.
- `—`를 습관적으로 쓰지 않는다. 짧으면 쉼표로 잇거나 한 문장으로 끝낸다.
- 기술 용어는 업무에서 쓰는 그대로 두고, 설명하려고 풀어쓰지 않는다.
- 반대로 `~했음`, `이거 수정`처럼 메모식으로 흐르지도 않는다.

| AI가 정리한 티 | 자연스러운 표현 |
|---|---|
| 운영 DB에서 구 테이블을 참조하던 잔존 FK 6개 정리 — 모두의서평 등록 실패 해소 | 운영 DB에 남아있던 구 테이블 FK 6개 정리, 모두의서평 등록 오류 수정 |
| 도서 삭제 기능 구현 — 연관 콘텐츠가 있는 도서는 삭제를 차단하고 종속 데이터 처리까지 반영 | 도서 삭제 기능 구현, 연관 콘텐츠가 있는 경우 삭제되지 않도록 처리 |
| 도서 카테고리 관련 작업: DB 컬럼 변경 이력이 있어 수정 전 실제 컬럼명 재확인 필요 | 도서 카테고리 관련 수정 전 실제 DB 컬럼명 확인 필요 |

## 5. 시행착오와 의사결정 구분

**시행착오 자체는 기록하지 않는다.** 최종 결과에 영향을 주지 않았다면 아래는 남기지 않는다.

- 처음 잘못 판단한 원인, 실패한 구현 방식
- 수정했다가 되돌린 과정
- 단순 병합 과정, 충돌 없이 자동 병합됐는지 여부
- 문제 해결 중 쓴 일시적인 우회 방법

**단, 이후 작업 범위나 정책에 영향을 주는 의사결정은 남긴다.**

- 의도적으로 이번 범위에서 제외한 기능, 이후 추가 작업이 필요한 범위
- 정책 결정이 필요한 사항, 기술적 제약 때문에 적용하지 않은 방법
- 다음 작업자가 알아야 하는 중요한 결정

예: `도서 목록 조회 성능 개선, 기본 조회 구조를 2단계로 변경. 리뷰수·평균별점 정렬은 이번 범위에서 제외`

## 6. 분량 기준

- 작업이 많은 날도 **완료된 작업 3~5개** 정도로 그날 핵심 업무가 파악되는 수준을 목표로 한다.
- 다만 개수를 맞추려고 서로 다른 업무를 억지로 합치지 않는다.
- 읽었을 때 아래 세 가지에 바로 답할 수 있으면 충분하다: 오늘 무엇을 했는가 / 무엇이 해결됐는가 / 아직 남은 문제는 무엇인가

## 7. 작성 형식

```markdown
# YYYY-MM-DD 일일 업무 보고

작성자: {이름}

## 완료된 작업
- ...

## 진행 중 / 이슈
- [이슈명]: 현재 상황 → 다음 액션
```

## 8. 기타

- 오늘 날짜(내 사용자ID)의 파일이 없으면 새로 만들고, 있으면 이어서 추가한다.
- 지난 날짜 파일은 수정하지 않는다.
