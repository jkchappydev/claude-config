# 일일 워크로그 작성

## 파일 경로

`docs/worklog/YYYY-MM-DD-{사용자ID}.md` — 날짜와 작업자로 나눈다. 같은 프로젝트에 여러 사람이 워크로그를 써도 파일이 충돌하지 않게 하기 위함.

## 1. 작성자 판별 (파일 생성 시 1회)

1. `git config user.email`로 현재 Git 사용자 이메일을 확인한다.
2. `~/.claude/references/worklog-members.local.md`(사용자ID | 이름 | Git 이메일 표)에서 해당 이메일을 찾는다.
   - 파일이 없으면 템플릿(`worklog-members.md`)을 복사해서 만들라고 안내한다.
3. 매핑을 찾으면: 그 사용자ID를 파일명에, 그 이름을 "작성자"에 쓴다.
4. 매핑이 없으면:
   - 파일명 사용자ID는 이메일의 `@` 앞부분을 그대로 쓴다.
   - 작성자 이름은 **추측하지 않는다** — Git author name이 있으면 그걸 쓰고, 없으면 이메일을 그대로 쓴다.
5. 한 사람이 여러 Git 이메일을 쓰는 경우 매핑 표에 같은 사용자ID·이름으로 여러 행이 있을 수 있다.

## 2. 정보 출처 우선순위

작업 내용을 정리할 때 아래 순서로 참고하고, 우선순위가 낮은 자료로 높은 자료의 내용을 지우지 않는다.

1. **기존 워크로그** — 오늘 이 파일에 이미 적힌 내용(대화 중 논의·결정 등)
2. **해당 날짜의 Git commit** — 해당 작성자 이메일 기준
3. **Git 변경 내역(diff)** — 커밋 메시지만으로 뭘 했는지 불충분할 때 실제 변경 내용을 참고

Git commit이 없다고 해서 워크로그에 이미 적힌 업무(운영 DB 작업, 서버 설정 변경, 장애 대응, 테스트, 분석 등)를 빼지 않는다. Git은 워크로그를 보완하고 작업자·실제 변경사항을 확인하는 보조 자료로만 쓴다.

## 3. 커밋을 작업 단위로 묶기

- 여러 커밋이라도 목적이 같으면 하나의 작업 항목으로 합친다. 커밋 메시지, 변경 파일, 기존 워크로그 내용을 함께 보고 같은 작업인지 판단한다.
  - 예: `fix: 도서 삭제 오류 수정` / `fix: FK 처리 추가` / `fix: 댓글 cascade 추가` / `test: 삭제 테스트 수정` → "도서 삭제 기능 및 연관 데이터 삭제 처리 보완" 한 줄로 통합
- merge commit, 포맷팅, 오타 수정, 빌드 산출물 자동 변경 등 보고 가치가 낮은 커밋은 독립 항목으로 만들지 않는다 — 관련 작업에 흡수하거나 생략한다.

## 4. 작성 원칙 (간결화)

이 보고는 개발 기록이 아니라 **"오늘 무엇을 했는지 빠르게 파악"**하는 용도다.

- 한 작업은 기본적으로 한 줄. **무엇을 했는지 + 결과** 중심으로 쓴다.
- 클래스명·메서드명·파일명 등 구현 세부사항은 꼭 필요한 경우가 아니면 뺀다.
- 장애나 중요 이슈가 아니면 상세한 원인 분석은 생략한다.
- 사소한 수정은 독립 항목으로 만들지 않고 관련 작업 항목에 포함한다.
- 다만 중요한 기술적 의미나 결과는 과하게 축약하지 말고 남긴다 — 무조건 짧게 쓰는 게 목적이 아니라 빠르게 파악되는 게 목적이다.
- 항목마다 작성자 이름을 반복해서 붙이지 않는다 — 파일 자체가 사용자별로 분리되어 있기 때문.

## 5. 작성 형식

```markdown
# YYYY-MM-DD 일일보고

작성자: {이름}

## 완료된 작업
- ...

## 진행 중 / 이슈
- [이슈명]: 현재 상황 → 다음 액션
```

## 6. 기타

- 오늘 날짜(내 사용자ID)의 파일이 없으면 새로 만들고, 있으면 이어서 추가한다.
- 지난 날짜 파일은 수정하지 않는다.
